# DiscoveryBench 동시 요청 24 / 서버 max-num-seqs 24

이전 `discovery_gate60_d8_s8_20260929`의 16/16 실행과 부하 수준을 비교한다.
입력 파일은 원본 DiscoveryBench replay 256개와 바이트 단위 동일하다.
기존 실험 결과·설정·스냅샷은 수정하지 않는다.

|항목|이전|이번|
|---|---|---|
|클라이언트 최대 진행 요청|16|24|
|vLLM max-num-seqs|16|24|

|청크 / 복사 작업자|128토큰 / 1개|동일|

|조기 준비 알림 / 대기열 취소|OFF / OFF|동일|
|cold / warm|256요청 / 256요청|동일|

각 조건은 새 프로세스·빈 DRAM/staging·새 DAOS namespace에서 시작한다.
cold 완료 후 비동기 복사와 staging을 drain하고, 같은 프로세스·DRAM·DAOS 캐시로 warm을 실행한다.
rolling 투입이며, 모든 요청이 끝날 때까지 기다리는 묶음 방식이 아니다.
총 3조건 × 512요청 = 1,536요청, 조건별 1회이다.

60% 정책은 할당 직전 전체 staging 사용량이 4.8GiB 이상이면 새 DRAM 프리페치를 생략한다.
DAOS 프리페치·진행 중 복사는 유지하며, 허용된 배치가 60%를 넘기는 것은 가능하다.
vLLM 자원 한계 때문에 실제 계산 중인 요청 수는 항상 24개가 아닐 수 있다.

## 비교 해석

- 16/16 vs 24/24는 부하 수준 비교다. 클라이언트 수만 바꾼 실험은 아니다.
- 정책 효과는 이번 24/24 안의 OFF·ON·gate60끼리 우선 비교한다.
- cold/warm을 나누고 hit·새 입력 계산량·생성량·staging 피크·차단·용량 실패 재계산을 함께 기록한다.
- 이전 데이터는 `previous_gate_summary.json`에 복사해 비교 표에 포함한다.
- 요청 목록이 같아도 완료 기반 도착 시각과 캐시 재사용량은 달라질 수 있다.
- 조건별 1회로 통계적 우열을 확정하지 않는다.
- 조건 종료 후 해당 실험 namespace만 삭제하며, 공용 컨테이너·기존 캐시·로그는 보존한다.

`status.json`에 진행 상황, `service.log`에 로그, `RESULT_KO.md`에 완료 조건별 결과와 그래프를 저장한다.
