# GovReport 실행 결과와 해석

## 결론

요청한 Qwen3-14B, DRAM8GiB, GPU staging8GiB, 동시 요청16 조건에서 DRAM 프리페치 OFF/ON 실행을 완료했다. 조건별 cold200 → warm200으로 총800요청 모두 성공했다.

그러나 **이번 워크로드는 DRAM 프리페치의 유불리를 측정하는 데 적합하지 않았다.** 양쪽 warm에서 DRAM lookup hit는 0개였고, ON의 DRAM 프리페치 제출·GPU 복사도 모두0회였다. 스위치는 켜져 있었지만 실제 DRAM 복사 작업은 실행되지 않았다.

## 왜 DRAM hit가 없었나

GovReport는 서로 다른 긴 보고서를 요약하는 작업이다. 이번 입력200개의 토큰 합계는2,083,583개, 평균10,417.915개다. 입력 KV만 계산해도 약341GB(10억 바이트 기준)로 DRAM8GiB보다 훨씬 크다.

cold가 끝날 때 DRAM에는 최근 캐시 약7.99GiB가 남아 있었다. warm은 문서 목록의 처음부터 다시 시작했다. 앞쪽 문서를 읽으면서 DRAM 내용이 계속 갱신되므로, 뒤쪽에 남아 있던 캐시를 다시 조회하기 전에 밀어내는 순차 스캔 형태다. 실제 계측에서 DRAM hit는0, DAOS hit는16,175청크였다. 모든 캐시가 DRAM에 없어서 문제가 생겼다는 뜻이 아니라, **조회 시점에 필요한 캐시가 DRAM에 없었다**는 뜻이다.

DRAM 프리페치 연구에는 같은 문서를 가까운 시점에 다시 사용하는 자연스러운 다중 질문·수정 요약 워크로드 등이 필요하다. 이 실행의 데이터 순서를 사후 변경하거나 캐시를 강제로 고정해 프리페치 효과를 만든 것은 아니다.

## DAOS hit100%인데 왜 재계산하나

lookup hit는 DAOS에 데이터가 있다는 뜻이다. 해당 데이터를 GPU staging에 올리는 데 성공했다는 뜻은 아니다. 긴 요청이 겹쳐 staging 공간이 부족하면 읽기 일부가 실패하고 사용할 수 없는 prefix 부분을 다시 계산할 수 있다.

요청별 DAOS 조회·읽기 결과와 HTTP 응답의 실제 cached_tokens를 대조했다. 이번 실행의 재계산 원인 귀속 불일치는0건이었다. OFF는 입력 번호0,1,10,12,15, ON은3,4,10,12,14,59에서 용량 부족에 따른 재계산을 확인했다. CUDA OOM 및 vLLM preemption 로그는 없었다.

두 조건 모두 각 단계 시작 전 staging=0을 확인했다. 최대7.988GiB라는 것은 실행 중 순간적으로 거의 가득 찼다는 뜻이며 이전 조건의 데이터가 남아 있었다는 뜻은 아니다.

## 실험 조건과 한계

- LongBench의 GovReport200개 전체를 원래 순서로 재생했다. 원본 GovReport 전체 데이터셋이나 DiscoveryBench agentic 실행은 아니다.
- 모델 Qwen3-14B BF16, 청크128, vLLM max-num-seqs16, DRAM/staging 각8GiB, 직접 오브젝트 경로.
- DRAM 프리페치만 OFF/ON, DAOS 비동기 프리페치는 둘 다ON. 복사 작업자1, 대기열 취소 및 조기 준비 알림OFF, soft watermark 없이 물리적 용량만 적용.
- 조건마다 새 프로세스·빈 DRAM·독립 DAOS namespace. cold와warm 사이에는 캐시를 유지하고 비동기 작업 및 staging만 drain했다.
- 요청 하나가 끝나면 다음 요청을 넣는 rolling 방식. 같은 입력 순서와 동시성 상한이지만 실제 도착 시각까지 동일하지는 않다.
- 한 페이지 요약 프롬프트, 출력 최대512토큰, 정상 EOS. 출력 평균 약458토큰이다. 32K 한도를 넘는3개 문서는 앞/뒤를 남겨 축소했고, 모든 실제 prompt_tokens가 준비 단계와 일치했다.
- 최대 길이로 종료된 요청은 cold OFF43개/ON54개, warm OFF38개/ON40개다. 요약 품질 점수는 평가하지 않았다.
- 조건당1회이므로 반복 측정에 의한 통계적 유의성은 평가하지 않았다. 전체 시간에 서버 시작 및 종료·최종 비동기 저장 drain 시간은 포함하지 않는다.
