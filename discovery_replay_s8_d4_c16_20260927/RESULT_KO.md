# DiscoveryBench 고정 입력 재생: DRAM 프리페치 OFF/ON

## 이번 실행의 핵심 결과

동시 요청 16개, GPU staging 8GiB, DRAM 4GiB에서 OFF/ON 각각 256개, 총 512개
요청이 정상 완료됐다. 지난 10GiB/8GiB 실험과 입력 256개는 동일하다. 모든 조건의
입력 토큰 합계는 1,578,438개다. 측정 코드 해시·네이티브 라이브러리 일치,
각 조건의 초기 빈 DRAM을 확인했고, 실행 후 실험 서버는 종료했다.

| 지표 | OFF | ON |
|---|---:|---:|
| 평균 TTFT | 1,645.37ms | 1,810.20ms |
| 평균 요청 완료 지연 | 6,079.25ms | 6,245.41ms |
| 256개 전체 처리 시간 | 167.86s | 165.21s |

ON의 백엔드 할당 실패 271회는 **DAOS 읽기 266회 + 저장 5회**다. 이를 요청 271개의
실패로 해석하면 안 된다. DRAM fallback 56회는 별도 집계이며 CPU 원본 경로로 처리됐다.
저장 실패 5회 중 2회는 일부 청크만 저장했고, 3회는 해당 저장 시도에서 0개를 저장했다.
추론 요청 자체의 오류, 음수 참조 카운트, 비동기 DRAM 복사 오류는 없었다.

### 공간 경쟁의 구체적 증거

첫 부분 읽기 요청 `chatcmpl-a88630d4c210e96a-b8673637`은 DAOS 청크 66개를
요청했으나 선행 연속 청크 35개만 반환했다. 해당 읽기 구간의 occupancy sample
`time_ns=1790435419727782522`에서 실제 할당량은 7.988GiB였고, 이미 준비된
DRAM 프리페치 객체가 약 5.02GiB, DAOS 프리페치 객체가 약 1.58GiB를 차지했다.
나머지는 준비 완료로 표시되지 않은 할당량이다. 이는 DRAM/DAOS가 같은 staging
풀을 점유한 상태에서 읽기용 공간이 부족했던 구체적 사례다.

8GiB에 20MiB 청크 409개가 들어가면 7.988GiB가 되며, 남은 공간은 다음 청크
하나를 담기에 부족하다. 따라서 최대치가 정확히 8.000이 아니어도 고갈이 발생한다.
전체 15개 부분 읽기는 합계 550개 청크를 요청해 139개를 반환했다. GPU 할당 실패
뿐 아니라 첫 실패 뒤 성공한 청크도 버리는 prefix 규칙이 적용되므로, 이 차이
411개를 할당 실패 266회와 동일시하면 안 된다. 반환하지 못한 범위는 재계산된다.

**이번에는 DAOS 읽기가 staging 공간 부족으로 제한되는 현상을 확인했다.**
그러나 전체 처리 시간은 약 1.58% 짧고, 평균 TTFT는 약 10.02% 길었다.
전체 처리 시간은 각 묶음의 마지막 요청에 좌우되며, TTFT는 개별 요청의 첫 응답
대기 시간이다. 생성 토큰도 OFF 69,004개 / ON 68,449개로 달라서 두 지표가 반대
방향으로 움직이는 것이 모순은 아니다. 조건별 1회 실행이므로 성능 차이의
통계적 유의성이나 보편적인 처리량 저하까지 입증한 것은 아니다.

지난 실험의 DAOS hit는 16개 OFF 1.25%, ON 1.45%였다. 이번에는 더 높지만,
DRAM과 staging 용량을 함께 바꿨으므로 과거 대비 모든 성능 차이를 DRAM 용량
하나만의 효과로 단정하지 않는다. 현재 OFF/ON끼리는 용량과 실행 설정이 동일하다.

## 실험 방법

- Qwen3-14B BF16, 청크 128토큰, DRAM 4GiB, GPU staging 8GiB, object 경로.
- 기록된 DiscoveryBench 모델 호출 256개의 입력을 시간순으로 선정하여 모든 조건에 동일하게 재생했다. Python 도구는 다시 실행하지 않았다. 전체 에이전트 벤치마크/정답 평가가 아니다.
- 동시 요청 16 × DRAM 프리페치 OFF/ON. 각 조건마다 새 vLLM 프로세스, 빈 DRAM, 새 DAOS 이름 공간으로 시작했다. 공용 캐시 삭제나 서버/OS 캐시 초기화는 하지 않았다.
- 16개씩 함께 보내고 해당 묶음이 모두 끝나면 다음 묶음을 보냈다. 요청 목록/순서/묶음 구성은 고정이지만 벽시계 도착 시각까지 같지는 않다.
- temperature=0, seed=0, thinking OFF, 최대 생성 2048토큰, EOS 허용. 생성량 차이는 별도 기록한다. 응답은 다음 입력에 반영하지 않는다.
- OFF는 DRAM→staging 프리페치만 끈다. DAOS 프리페치, GPU-direct 쓰기, 비동기 DRAM 저장/읽기 승격은 양쪽 모두 켰다.
- ON은 사전 watermark 제한 없이 실제 8GiB 풀에 할당을 시도한다. 실제 공간 부족 시 DRAM 원본으로 fallback한다. DAOS의 기존 serializer 제한은 유지했다.
- 모델 로딩 시간은 제외했다. 매 조건 첫 요청의 cold 영향은 포함했다. 각 조건 1회이며 순서는 c16_off → c16_on이다.

## 해석 시 주의

이 실험은 동일 입력에 대한 공간 사용/지연 진단이다. 생성 토큰 수, 실제 hit 비율, 완료 순서가 달라지면 실행 시간이 프리페치 효과만을 뜻하지 않는다. `comparison.json`에서 출력 동일성과 생성 토큰 합계를 확인한다. 시간에 따른 DRAM 승격/LRU도 성능의 일부다.

staging 최대치가 설정 용량에 가깝고 실제 할당 실패·fallback·DAOS 부분 읽기가 함께 늘어나는지를 확인해야 공간 경쟁의 증거로 해석할 수 있다. 그런 징후가 없으면 이번 입력은 한계를 드러내지 못한 것이며 경쟁 때문에 느려졌다고 결론 내리지 않는다.

원시 증거: `requests.json`, 각 조건의 `replay_calls.json`, `waves.json`, `config.yaml`, `trace.*.jsonl`, `server.log`, `initial_sample.json`, `final_sample.json`. 코드/입력 해시 및 라이브러리 일치 검사는 `validation.json`에 저장했다.

최초 코드 스냅샷과의 차이 및 실제 후처리 코드 해시는 validation.json에 명시했다. 백엔드 저장용 할당 실패를 DAOS 읽기 실패와 구분하여 해석한다.

## 16개 동시 요청에서 관측한 공간 사용

- ON staging 최대 7.988GiB. 용량의 90%(7.2GiB) 이상인 시간은 약 1.40초(전체의 0.85%)였다. 최대치만으로 지속적인 포화를 판단하지 않는다.
- DRAM 실제 할당 실패/fallback 56회. 이미 DRAM에 있던 캐시는 CPU 경로로 사용한다.
- 백엔드 할당 실패 271회. 저장 입장 제한 경고는 5회이며, 각 시도에서 저장 가능한 청크 수는 [15, 0, 0, 0, 4]였다. 이는 이번 저장 시도의 일부/전체 생략이며 영구적인 KV 손실이나 추론 실패를 뜻하지 않는다.
- DAOS GPU-buffer-full 읽기 경고 266회, 부분 DAOS 읽기 15회. 0회라면 DAOS 읽기 방해가 관측된 것은 아니다. 발생했다면 해당 시점의 DRAM/DAOS 점유량과 OFF 결과를 함께 대조해야 한다.
- 전체 시간 OFF 167.86초 / ON 165.21초. 1회 실행의 작은 차이를 유의미한 성능 악화로 해석하지 않는다. 평균 TTFT는 OFF 1645.37ms / ON 1810.20ms였다.
- DAOS lookup hit 비율은 약 17.76%였다. 이 워크로드에서 실제 발생한 비율이지 사전에 강제한 비율이 아니다.

용량 도달, fallback, 저장 제한, DAOS 부분 읽기는 서로 다른 증거다. 실제 발생한 항목만으로 해석하며, 용량 도달만으로 전체 성능 악화를 단정하지 않는다.

주의: `Local cpu memory under pressure`는 LMCache의 기존 고정 경고 문구다. 이번 GPU-direct store에서는 GPU allocator를 사용하므로, 이 경고를 DRAM 용량 부족으로 해석하면 안 된다. 실제 GPU 할당 실패 이벤트와 직전 CPU/DAOS ready 점유량은 `c16_on/allocation_failure_evidence.json`에 저장했다.
