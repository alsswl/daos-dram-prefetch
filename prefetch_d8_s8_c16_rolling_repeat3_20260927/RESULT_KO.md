# DRAM 8GiB / staging 8GiB / 동시 요청 16: 프리페치 비교

Qwen3-14B BF16, object 경로, 청크 128. 동일한 DiscoveryBench 기록 입력 256개를 재생했다. 처음 최대 16개를 보내고 하나가 완료되면 다음 입력을 즉시 투입한다. 묶음 전체 완료를 기다리지 않는다. Python 도구를 재실행한 full agentic 실험은 아니다. 매 실행은 새 vLLM 프로세스, 빈 DRAM, 새 DAOS namespace에서 시작한다. 서버/OS 캐시를 flush하지 않았다.

OFF/ON은 DRAM→GPU staging 프리페치만 바꾼다. DRAM 보관, DAOS 프리페치, 비동기 쓰기 미러·읽기 승격은 모두 유지한다. ON은 soft watermark 없이 실제 GPU 할당을 시도한다. vLLM max-num-seqs는 기존 16을 유지하고 클라이언트 동시 요청만 16로 제한했다.

각 조건 3회, 총 1,536요청. 실행 순서는 OFF→ON→ON→OFF→OFF→ON이다. 생성은 temperature0, seed0, 최대2048토큰, EOS 및 Observation 종료를 허용한다. 모델 로딩은 시간에서 제외하고 첫 cold 요청부터 마지막 요청 완료까지 측정했다. 요청 완료에 맞춰 다음 입력을 투입하는 closed-loop 방식이다. 총 256개와 최대 동시성 16은 고정하지만 서버 도착 시각과 완료 순서는 OFF/ON에서 달라질 수 있다. 마지막 요청들이 끝나는 구간은 새 입력이 없어 동시성이 감소한다. 워커 인계에 짧은 공백이 있어 정확히 모든 순간에 16개인 것은 아니다.

## 지표와 한계

Hit 비율은 lookup 청크 기준이다. 실패 재계산율은 전체 입력 토큰 중 DAOS GPU 할당 실패로 잃은 usable prefix 토큰 비율이며 cold miss를 분자에서 제외했다. 실제 usage.cached_tokens로 검증했다. 프리페치가 캐시 승격·퇴출 시점에 미친 영향까지 포함하며 고정된 hit trace 실험은 아니다. 생성량 차이 때문에 전체 시간 차이를 순수 I/O 개선량으로 해석하지 않는다. 3회 반복은 변동 확인을 위한 작은 표본이며 보편적인 성능 우위를 증명하지 않는다.

## 이번 관측의 요약

- 3회 평균 TTFT: OFF 385.08ms, ON 390.59ms. ON이 약 1.43% 길었으며,
  반복별 차이 방향도 일정하지 않아 명확한 TTFT 개선으로 볼 수 없다.
- 전체 처리 시간: OFF 평균 102.53초, ON 평균 100.02초(약 2.44% 짧음).
  평균 생성량은 OFF 68,797토큰, ON 68,409토큰으로 달라 순수 전송 개선량으로 해석하지 않는다.
- 평균 진행 중 요청 수는 OFF 15.51, ON 15.47이었다. 모든 실행에서 첫 16개가 모두
  끝나기 전에 후속 요청이 시작됐고, 진행 중 요청은 16을 넘지 않았다. 마지막 drain은 포함한다.
- ON staging 최대는 반복별 5.684/5.586/3.359GiB였다. DRAM 프리페치 fallback은
  세 번 모두 0, DAOS 실패 재계산율도 OFF/ON 모두 0%였다. 이번에는 공간 경쟁의
  징후가 줄었지만 그것이 곧 TTFT 개선을 보장하지는 않았다.
- ON staging이 비어 있던 시간 비율은 약 80.3~81.8%였다. 지속적인 요청 처리가 곧
  지속적인 staging 점유를 뜻하지 않는다. staging은 전달 후 반환하는 임시 버퍼다.
- DRAM lookup hit는 OFF 평균 89.66%, ON 평균 89.26%; DAOS는 양쪽 약 1.0%였다.
  따라서 DAOS 읽기 비중이 높은 혼합 부하의 결과로 일반화하면 안 된다.
- 입력·코드 스냅샷·설정·native 라이브러리·빈 초기 캐시·최종 버퍼 반환 검증을 통과했다.
  6개 실행에서 저장 오류 및 요청 오류가 없었다. 모든 실험 서버는 종료했다.
